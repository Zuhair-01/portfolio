Ostazi (ostazi.sy)

A real, deployed two-sided tutoring marketplace for Syria: students and parents book verified private tutors on a cash-first commission model. Built solo, end to end.

Next.jsExpressPostgreSQLPrismaCapacitor
Unlike the other five projects, Ostazi's source is kept in a private repository — it handles real bookings and real commission accounting. This page is a case study, demonstrated live rather than published as open source.

01Problem

Finding a qualified private tutor in Syria happens informally, through word of mouth — no verification, no scheduling system, and no accountability if a tutor cancels last-minute or a payment dispute comes up.

02Why it matters

Education access in Syria depends heavily on private tutoring, but there was no trusted, structured way to find and book one. A cash-first model was a deliberate choice for a market where digital payment rails are limited.

03Solution

A full marketplace: phone/OTP authentication (no passwords), an admin-driven teacher verification workflow, a real booking state machine with cancellation rules and no-show accountability for both sides, and a versioned commission ledger that survives rate changes without corrupting historical bookings.

04Architecture

Next.js (Arabic RTL + English, next-intl)
  -> Express/Node API
       - phone + OTP auth (no passwords)
       - teacher verification (PENDING -> VERIFIED/REJECTED/SUSPENDED)
       - booking state machine (REQUESTED -> CONFIRMED -> COMPLETED,
         or CANCELLED/NO_SHOW with actor tracking both sides)
       - commission engine: versioned + snapshotted per booking,
         append-only ledger, teacher risk-tier escalation
       - review/rating system with a flag-and-moderate pipeline
  -> PostgreSQL (Prisma) on Supabase
  -> Deployed on Vercel; Capacitor wraps the same app for Android/iOS

05Technical decisions

Commission is versioned, never mutated. The rate is snapshotted per booking, so a later rate change never silently rewrites historical bookings — the ledger itself is append-only, not a mutable balance field.

Risk-tier escalation actually blocks bookings. A teacher's outstanding debt escalates them through NORMAL to WARNING to RESTRICTED to BLOCKED, and BLOCKED genuinely prevents new bookings — not just a dashboard label.

A real gap was found and fixed during development: originally only teachers could report a student no-show, leaving no way for a student to report that a teacher simply didn't show up. Fixed with a symmetric reporting path for both sides.

06Security

No passwords anywhere — phone + OTP only. Admin accounts cannot be created through public registration, only via a CLI script. A P0 issue (a debug flag that could have exposed OTP codes outside development) was found and fixed via the hosting platform's API, verified in production, and documented internally rather than silently patched. Legal documents (Terms of Service, Privacy Policy, Cancellation/Refund Policy, Commission Policy) exist in draft form, explicitly marked as not yet reviewed by legal counsel.

07Limitations

  • Chat, in-app notifications, and a real SMS gateway aren't built yet (OTP is currently echoed directly for dev/preview testing, not sent via SMS).
  • ShamCash (a common local payment method) has an architecture placeholder but is disabled pending integration.
  • Native app store publishing hasn't happened yet — the Capacitor mobile shell exists but isn't distributed.

08Future improvements

  • Real SMS OTP delivery.
  • ShamCash payment integration.
  • In-app chat and notifications.
  • Native app store submission.
