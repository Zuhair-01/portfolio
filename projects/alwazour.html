01Problem

A real business with a real catalogue and no way to show it online. Phase 0 was a reality audit, and it was blunt: greenfield. No repository, no product data, no assets, no existing website, no analytics, no prior SEO. Every section of the original brief that said "audit the existing codebase" had nothing to audit.

The hard part was not the code. It was deciding, without the client available on demand, what the site was allowed to be, and building it so the owner could keep using it after I left.

02Approach: phases with a done condition

The project ran as an approved master spec with numbered phases, and each phase carried its own completion condition. Phases 0 to 11 are covered: reality audit, infrastructure validation, business and market intelligence, brand DNA, data architecture, design exploration, design system, frontend foundation, product experience, solutions, and admin/operations.

Commercial and later phases were never started, and the spec says so rather than pretending otherwise. A plan that pretends to be finished is worth nothing to the person who has to run the site.

03Data before pixels

The catalog was designed as data first: a product schema, a CSV import path, an admin database layer and a resolveProductQuery resolver, finished and visually verified before any page design was locked. It carried 47 tests at that point.

This ordering is why the search and filter on the live catalog work. Search was never a styling decision; it was a consequence of structuring the products properly the first time.

04Design: three directions, scored

Phase 5 built three design directions, screenshotted both languages and both viewports, and scored them. Direction A won 31/35 and became the token set in src/site/tokens.ts. The first pass of that system read as flat, so the accent and shadow layers were reworked after direct feedback rather than defended.

Arabic was designed, not translated. The system uses a single font family and drops letter-spacing for Arabic, because the same tracking that makes Latin look good makes Arabic look broken.

05What actually works on the live site

Real catalog search. Client-side text search, category filtering, an empty state and URL-parameter preselect, all confirmed interactively in the browser rather than assumed from the code.

Solution pages that resolve. A solution page genuinely pulls matching products out of the catalog through the resolver, proven against real sample data, with 7 new tests covering it. Not hardcoded cards.

An admin the owner can run. Products CRUD, lead capture and analytics, plus spreadsheet import that extracts rows into human-reviewed candidates and confirms them through the normal product form. It was security-hardened and tested end to end, including a real browser upload.

A real inquiry path. The point of the site is that an enquiry reaches the owner. It is the flow the business runs on, which is why it is the flow I show clients.

06Verification, as it actually stands

  • 82 tests passing across five suites: search normalisation 14, CSV import 18, solution resolution 7, site build 21, measurement and lead handling 22.
  • One suite, server/shipment-import.test.mjs, currently fails to load on this machine.
  • Root cause, confirmed by reading the installed package: package.json pins SheetJS from the official CDN build (0.20.3), but the node_modules copy on disk is the old registry version 0.18.5, where XLSX.set_cptable no longer exists. The source is written against the pinned build.
  • Fix: reinstall dependencies from the pin (npm ci). I did not run it here because it downloads packages and the working tree carries uncommitted changes from an earlier session that are not mine to overwrite.
Why I am writing this down: a portfolio that claims "all tests pass" is worth nothing the first time a client opens the repo. This is the real state, including the part that is not working.

07What is not done

  • Commercial flows are not built: B2B and project work, custom-cable orders and repair requests were never started.
  • Phases 12 to 18 of the spec are not started.
  • The Latin brand form is still a transliteration choice awaiting the owner's confirmation. The Arabic name is the one used on the site, and the Latin name is a decision, not a translation.
  • No public result numbers are claimed for this project. The owner uses the site daily, and that is a capability claim, not a measured result.

08What I took from it

Data before pixels, and design decided by comparison instead of taste. And the handover question, which is the one that decides whether a client build succeeds: the site had to be usable by a shop owner who is not technical, in Arabic, on a phone, while updating products and reading inquiries. Everything else in this case study is downstream of that requirement.
